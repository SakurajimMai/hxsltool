# PayPal 付款级人工积分核对

2026-09-08。已实现的路径是**管理员核对商户记录后确认本站积分权益**，不是自动认定 PayPal 实际资金归属，也不会调用退款、收款、接受索赔或提交证据接口。真实商户 Sandbox、自动财务对账及完整 Goal 仍未验收。

## 操作路径

管理员 → 建筑 AI → 支付与对账 → 人工核对付款积分。

1. 选择已关联本站验证付款的争议，读取整笔付款摘要、已验证退款、允许范围及上次核对状态。
2. 在受限商户系统中核对全部关联款项。输入整笔付款最终撤销总额（USD，**包含已退款金额**，重叠部分只算一次，不含手续费），以及内部核对记录编号；不要填写个人资料或秘密。
3. 确认已核对退款重叠与赔付归属，提交前再次确认。服务端逐请求管理员授权、同源/CSRF、15分钟近期认证，不接受客户端提供操作者。
4. 服务端重读当前商户的全部已知关联案例（最多10个，顺序读取），重新校验版本和限额，再将不可变审批、积分回收与审计写入同一事务。网络请求不在数据库事务中。
5. 成功明确显示“人工积分核对”，不是“自动验款”。如果响应丢失，保持表单快照和请求编号，重试同一请求；不会重复记账。重新读取后才能另建修正版本，原证据不删除。

金额按整数美分保存，积分按整数毫积分向上舍入。例如19.90美元购买10积分，人工确认总撤销3.98美元后对应撤销2积分；此前暂挂的多余积分释放。已经消费的欠额如实保留，正在生成的冻结积分不被抢扣。

## 资格与失效

- 只允许存在本站已验证收据、全部已知案例已结案、没有未核实 NONE 后继或旧协议争议的付款。未结案、无收据、跨环境/商户、金额越界或不一致版本拒绝。
- 总额不能低于已验证现金退款，不能高于原交易金额或退款与关联争议金额形成的合理上界；后台没有任意调高技术限额的入口。
- 退款逐笔与累计快照取不重复的实际退款金额；审批输入为整笔总额，不能再把退款盲目相加。
- 新退款、较新争议状态、复议或关联案例会改变证据指纹，旧审批失效并重新进入待核对。暂挂保留此前已确认损失下界；较新胜诉状态本身不证明原现金损失已回到卖方，不能自动抹除审批。
- 并发审批和网络期间变化由前后两次版本校验拒绝。相同幂等请求可重放；相同编号不同参数拒绝。读成功不等于最终结算成功。
- 列表只输出白名单状态，不输出商户ID、付款ID、内部指纹、审批人或参考记录；同名案例按完整商户作用域读取，不能套用另一商户审批。

## 持久化及回滚

Schema7只增 `ai_paypal_settlements` 和不可更新/删除触发器，保留已有配置、用户、账本和schema6争议历史。初始化不会覆盖审批。记录含收据关联、证据摘要、金额、幂等摘要、管理员、内部参考编号及时间。

维护备份支持schema1–7，未知8及缺少对应表的快照拒绝。普通配置导出不包含审批/用户/账本。完整库备份属于受限敏感维护流程。

已有schema7财务数据不能直接切换至v6/v5代码继续收款或生成，它们不理解新的有效权益状态。优先前向修复，或使用同样支持schema7的已验证镜像；必须数据恢复时离线准备新路径，保留原库和快照，先核对快照之后的商户/生图未知窗口。不得删表降版本或删除生产卷。v7备份/应用重开及真实两镜像更新/兼容回退/离线恢复有隔离证据，见[容器演练](container-rehearsal.md)；不是旧schema降级或实际商户故障窗口恢复证明。

## 验证与限制

运行 `pnpm test:ai`、`pnpm test:ai:disputes`、`pnpm test:backup`、`pnpm lint` 和 `pnpm typecheck`。具体结果及报告在 [validation.md](validation.md)。浏览器确认核对使用真实服务和显式canonical客户端替身，管理员拒绝路径走真实HTTP；不是实际商户读取。

仍缺：真实商户最终赔付归属与退款关联自动核算、NONE后继/多交易分配、未支持事件与未知checkout完整恢复，三渠道实际Sandbox。人工核对不能替代上述完整验收，也不以关闭live开关宣称功能完成。
