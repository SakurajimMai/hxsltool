# PayPal 返回页与多次私有查询复盘（2026-09-08）

## 1. 根因分类

- B / 跨层契约、E / 隐含假设：本地 order.open 与 checkoutUrl 不能证明远端尚未付款。首轮 320px 异常截图中，捕获响应 unknown 后仍出现“继续结账”。另一次安全审查发现 canonical order 与 capture 各自有效，不代表两次查询关联到同一个本地订单。
- D / 覆盖缺口：原服务端捕获测试覆盖重复/未知状态，但没有覆盖新返回面板及订单列表里的恢复入口；单独对象归属检查不覆盖连续查询返回不一致对象。

## 2. 为什么初次实现不足

新组件沿用了通用结账链接的展示条件，并把“有链接”当作“可继续付款”。这不是视觉颜色问题。没有多次失败后猜测根因：实际截图、条件分支和新增断言共同确定问题。原返回页并不存在，不声称旧版本已有这一新 UI 缺陷。

## 3. 预防机制

| 优先级 | 规则 | 实现与证据 |
| --- | --- | --- |
| P0 | 返回 GET、URL token、订阅 ACTIVE 不作为扣款或授信事实 | 只读本地订单加载；明确 POST review；capture 独立同意；handler 与浏览器断言 |
| P0 | PayPal 订单列表先进入核对页；只有刚从私有 API 读到 approval_required 才给批准链接 | AiOrders / AiPaypalReturn；unknown 时返回面板和订单列表均无 Resume checkout |
| P0 | 核对完成付款不允许新发 capture；重试同一对象 | reviewPaypalOrder 仅 GET 上游；中断响应浏览器场景只有一次 capture 请求 |

# Creem 历史回收与取消被当前目录阻断（2026-09-08）

## 1. 根因分类

B / 跨层契约与 E / 隐含假设：同一个 subscription 读取函数无条件调用当前 Product，历史退款/争议与取消也调用了新授信的售价校验。旧订单被冻结，但当前目录可改价或归档，两者不应被视为同一份事实。

先增加 4 个用例：一次性改价后退款、无目录访问的订阅退款先到、改价后争议、无目录访问的取消。修复前 4 项分别因 PRODUCT_MISMATCH / STATUS_UNKNOWN 失败，旧 16 项通过。修改后 20 项通过；再追加新授信不放宽、退款关键身份/金额/环境、真实签名 handler 重试消除异常 3 项。
