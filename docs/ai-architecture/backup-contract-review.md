# Bug Analysis: SQLite 主文件复制不等于一致备份

## 1. Root Cause Category

- **B / E / D：跨层契约、隐式假设和测试覆盖缺口。** 应用使用 WAL，维护脚本却将文件系统中的主文件当成全部已提交数据库；恢复假设操作者已停止全部访问者，直接覆盖主库，没有处理旧 sidecars。
- 原文档中的 `backup:rehearsal` 不是当前 package.json 可执行命令。旧验收陈述不能作为新增 AI 订单/账本数据的恢复证据。
- 实际判别证据：同一个真实数据库 checkpoint 后写入管理员 session、AI 用户/配置/冻结账本，主库 raw copy 的用户数仍为 0；新固定读事务备份完整保留同一时点，另一连接在备份期间提交的 100 单位不污染快照。

## 2. Why Fixes Failed

未重复尝试表面修补。新测试首次遇到 Node SQLite null-prototype 返回对象与 strict literal 比较的测试适配问题；将两个被核算字段 spread 成普通对象后保留精确断言。没有将 warning、测试替身或进程重开当成数据恢复成功。

## 4. Systematic Expansion

- 同类风险：直接复制 `-wal/-shm` 三个文件也不能构成同时点一致快照；断流后漏停 worker/webhook 也不等于离线。
- 本轮顺带核验发现 worker 的既有 `test` 命令仅输出提示而未执行断言，不能作为 worker 回归通过证据；已有网页/处理包测试不替代其真实任务与引擎测试。该既有缺口应在全工具回归阶段补齐，不计为本轮已完成。
- 备份点之后的付款/消费/供应商投递是外部事实，不会随本地数据库倒退。恢复 queued 状态后自动派发可能重复付费；复用快照前登录/MFA 恢复码也可能复活被撤销凭据。
- 本轮不以新保护逻辑悄悄重写业务状态；相关真实差异对账和凭据恢复记录为后续完整验收，不能把 `prepared-offline` 当成上线许可。
